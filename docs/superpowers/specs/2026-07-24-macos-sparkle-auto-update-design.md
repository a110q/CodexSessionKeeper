# macOS 内网自动更新设计

## 背景

Codex 会话管理当前包含两个桌面实现：

- Windows Electron 应用已经通过公司内网 Mac mini 静态服务器完成
  `1.0.99 → 1.1.0` 更新验证。
- macOS 原生 SwiftUI 应用已有 `1.0.14` DMG。自动更新分支中已经包含 Sparkle 2、
  员工确认式更新界面、EdDSA 清单校验和静态发布工具，但尚未在最新同步提交上完成
  macOS 双版本构建与实机升级验证；现有已交付 DMG 仍只能由员工手动覆盖安装。

公司更新服务器位于 `192.168.10.54:18080`，使用 Homebrew Nginx 提供静态文件。
公司 Mac 均为 Apple Silicon（M 系列）。本项目不申请 Apple Developer ID，不做
Apple 公证，接受首次安装时可能出现的 Gatekeeper 提示。

## 目标

完成并验证 macOS 原生应用中与 Windows 一致的员工确认式内网更新体验：

1. 应用启动后自动检查更新，但不自动下载。
2. 发现新版本时显示版本号和更新说明。
3. 员工明确确认后才下载。
4. 下载完成并验证签名后，再由员工确认安装和重启。
5. 更新只替换应用本身，不修改 `~/.codex`、会话或备份数据。
6. 使用现有 Mac mini 静态服务器，不依赖 NAS，不改变 Windows 更新目录。

## 非目标

- 不支持 Intel Mac。
- 不申请 Apple Developer ID，不进行 Apple 公证。
- 不发布到 Mac App Store。
- 不自行实现下载器、解压器或特权安装助手。
- 不在本次工作中修改 Windows 更新实现。
- 不在 macOS 更新验证通过前把 Mac 安装包放到员工下载首页。

## 方案选择

保留自动更新分支已经采用的 Sparkle 2 更新控制器和自定义 SwiftUI 员工确认界面。
Sparkle 的用户驱动负责下载、提取、签名验证和安装事件，应用界面负责“稍后提醒”、
“立即更新”、“稍后重启”和“重启并更新”交互。

未选择自行开发更新器，因为自行处理包替换、权限提升、签名验证、失败恢复和重启
会显著增加安全与维护风险。未选择仅提供 DMG，因为这不能满足应用内发现和确认更新
的目标。

当前分支将 Sparkle 固定为 `2.9.4`。本轮保持该版本不变；升级 Sparkle 必须作为
独立变更重新测试。

## 现有实现基线

自动更新分支已经包含：

- `MacUpdateCoordinator`：定时检查、版本匹配、下载、备份排空和重启安装协调；
- `SparkleUpdateDriver`：把 Sparkle 下载与安装回调转交给应用状态机；
- `UpdatePromptView`：员工确认、下载进度、重启确认和错误提示；
- `ReleaseManifest` 与 `UpdateCheckClient`：签名发布清单和平台产物校验；
- `scripts/build_app.sh`：Sparkle 框架嵌入、固定内网地址和 ad-hoc 签名；
- `build-release-manifest.mjs`、`verify-release-directory.mjs` 和
  `publish-release.sh`：跨平台发布组装、校验和原子发布；
- `build-download-page.mjs`：员工下载首页生成。

本轮实施以同步后的最新远端提交为准，不重新实现这些组件。只有自动化测试证明存在
缺口时才修改对应逻辑。已知需要补齐的交付缺口是：独立候选路径、正式 DMG 产物、
员工确认门禁回归测试以及 macOS `1.0.99 → 1.1.0` 实机验证。

## 应用架构

### 更新控制器

macOS 应用在主进程中创建一个生命周期与应用一致的
`SPUStandardUpdaterController`。控制器使用 Sparkle 标准用户驱动显示更新窗口。

启动行为：

- 允许定期自动检查更新。
- 禁止自动下载更新。
- 禁止无用户确认的安装。
- 提供“检查更新…”菜单项，调用 Sparkle 的显式检查接口。

自动检查只读取更新清单。发现更新后，员工可选择稍后提醒或安装更新。下载完成且
签名验证通过后，Sparkle 再显示安装并重新启动确认。

### 更新清单

macOS 使用独立 Appcast：

```text
http://192.168.10.54:18080/codex-session-keeper/stable/macos/appcast.xml
```

测试阶段使用：

```text
http://192.168.10.54:18080/codex-session-keeper/testing/macos/appcast.xml
```

Appcast 至少包含：

- 机器可比较的构建号；
- 面向员工的版本号；
- 发布日期；
- 更新说明；
- `arm64` 更新 ZIP 的 URL、长度和 Sparkle EdDSA 签名。

macOS 与 Windows 使用不同目录，Windows 的 `release.json`、`latest.yml` 和安装包
路径保持不变。

### 更新产物

每个 macOS 版本生成两种产物：

- `CodexSessionKeeper-<version>-macos-arm64.zip`：供 Sparkle 应用内更新；
- `CodexSessionKeeper-<version>-macos-arm64.dmg`：供员工首次从网页安装。

ZIP 和 DMG 来自同一次已验证的应用构建。发布记录保存文件大小、SHA-256、应用版本、
构建号和架构。

### 版本策略

现有 `1.0.14` 不含 Sparkle，无法自行接入自动更新。因此先构建：

- macOS `1.0.99`：包含 Sparkle 的内部测试基线；
- macOS `1.1.0`：目标更新版本。

使用 `1.0.99 → 1.1.0` 验证完整更新链路。由于产品尚未向员工正式分发，不需要为
已部署员工迁移旧的 `1.0.14`。版本一经发布，其 ZIP、DMG 和 Appcast 引用不得在原
版本号下被重新打包替换。

## 更新签名与无证书边界

Sparkle 更新包必须使用 EdDSA 签名：

- 使用 Sparkle 官方工具生成更新密钥；
- 私钥只保存在指定构建 Mac 的登录钥匙串中；
- 私钥不得写入源码、Git、构建日志、安装包、Mac mini 或 NAS；
- 公钥写入应用配置；
- 发布前使用官方工具生成或验证 Appcast 签名。

应用和 Sparkle 内嵌组件采用 ad-hoc 签名，以保证应用包内部签名结构一致，但该签名
不代表 Apple 认可的开发者身份。

由于没有 Apple Developer ID 和公证：

- 首次通过浏览器下载 DMG 后，macOS 可能阻止直接打开；
- 员工可能需要右键选择“打开”，或在“系统设置 → 隐私与安全性”中选择“仍要打开”；
- 不编写脚本绕过 Gatekeeper，不移除隔离属性，不降低系统安全设置；
- 后续 Sparkle 更新是否仍出现系统提示，以公司 M 系列 Mac 的实机验证结果为准；
- 未通过实机验证时不得宣称 macOS 自动更新可正式使用。

静态服务器仍使用内网 HTTP。更新真实性与完整性依赖 Sparkle EdDSA 签名，网络边界
继续由固定私有 IP、Nginx ACL 和不开放公网端口共同限制。应用不得为了 HTTP 更新
设置无限范围的网络放行；如 macOS 网络策略需要例外，只允许满足该内网地址所需的
最小范围配置。

## 数据流

```text
应用启动
  → Sparkle 读取 testing/stable Appcast
  → 比较本地构建号与服务器构建号
  → 显示新版本和更新说明
  → 员工确认下载
  → 下载 arm64 ZIP
  → 校验长度和 EdDSA 签名
  → 员工确认安装并重新启动
  → Sparkle 替换应用包
  → 新版本重新打开
```

更新器只能操作应用包和自己的更新缓存。它不接收 `~/.codex`、本地增量备份目录或
快照目录作为输入。

## 错误处理

- Appcast 不可访问：保留当前版本，自动检查静默失败；员工主动检查时显示可重试错误。
- Appcast 格式或版本无效：拒绝更新并记录错误。
- ZIP 长度不一致或 EdDSA 签名错误：拒绝安装，保留当前应用。
- 下载中断：允许 Sparkle 按其标准机制重试，不运行部分下载。
- 安装权限不足：由 Sparkle/macOS 显示授权提示；不缓存管理员密码。
- 重启失败：应用包已安装时允许员工手动重新打开；记录可诊断状态。
- 任何更新失败不得删除、恢复或覆盖会话和备份数据。

## 测试策略

### 自动化与构建验证

- 现有 `swift test` 全部通过。
- 更新控制器的应用集成可在测试中替换为协议或适配器，验证应用只发起检查，
  不主动下载或安装。
- 验证“检查更新…”菜单调用显式检查入口。
- 验证 Appcast URL、公钥和自动下载设置写入最终应用包。
- 验证最终应用与更新 ZIP 仅包含 `arm64`。
- 验证版本号、构建号、文件长度和 Appcast 完全一致。
- 验证错误签名、损坏文件和错误版本不会进入安装路径。
- 扫描源码、构建目录、日志和发布目录，确认不存在 EdDSA 私钥。
- 验证 DMG、ZIP、Appcast 生成失败时构建脚本返回非零退出码。

### 内网实机更新

候选文件先发布到 `testing/macos`，不得直接覆盖 `stable/macos`。

测试前记录：

- 当前安装版本、应用哈希和安装路径；
- 会话总数、活跃/归档数量；
- 本地增量备份状态；
- 测试 Appcast、ZIP、DMG 的大小和 SHA-256。

测试步骤：

1. 在一台公司 M 系列测试 Mac 上手动安装 macOS `1.0.99`。
2. 启动一次，确认窗口、会话和增量备份正常。
3. 等待自动出现 `1.1.0` 提示，不主动触发隐藏接口。
4. 由用户亲自点击下载确认和安装重启确认。
5. 观察服务器访问日志、Sparkle 日志、应用进程和更新缓存。
6. 更新后确认应用为 `1.1.0`，窗口正常，会话数量不减少，增量备份继续运行。
7. 再次检查更新，确认显示已是最新版本。

首次安装或更新若被 Gatekeeper 阻止，记录实际提示和员工所需步骤，不自动绕过。

### 正式提升

只有自动化测试和实机测试全部通过后，才将与候选文件 SHA-256 完全相同的产物提升到
`stable/macos`。提升只复制已验证文件，不重新构建 `1.1.0`。

正式提升后从另一台内网 Mac 验证：

- Appcast GET 成功；
- ZIP 和 DMG HEAD/GET 成功；
- 文件长度和 SHA-256 与候选记录一致；
- Windows 更新端点仍正常；
- Nginx 只接受预期的只读请求。

## 员工下载首页

macOS 自动更新通过正式验证后，员工首页同时显示：

- Windows 当前版本、更新说明和安装包下载按钮；
- macOS 当前版本、M 系列芯片说明、DMG 下载按钮；
- macOS 首次打开时可能出现的 Gatekeeper 操作说明；
- 两个平台安装包的文件大小和 SHA-256。

首页只读取已发布的静态元数据，不提供上传、删除、登录或管理功能。

## 安全与运维边界

- 不操作 NAS。
- 不开放公网端口或路由器端口转发。
- 不改变 Windows 已验证的更新目录和文件。
- 不删除旧 DMG、Windows 安装包、更新缓存或临时传输文件。
- 不在测试通过前公开 macOS 下载入口。
- 管理员密码只由用户在 macOS 系统提示中输入，不记录、不传输。
- 发布失败时保留当前稳定版本与候选文件，禁止用不完整文件覆盖稳定目录。

## 完成标准

以下条件全部满足后，macOS 自动更新才算完成：

1. macOS `1.0.99 → 1.1.0` 在公司 M 系列 Mac 上由用户确认后成功。
2. 未确认时不会下载或安装。
3. 错误签名和损坏文件被拒绝。
4. 更新前后会话数量不减少，增量备份状态正常。
5. 首次无证书安装步骤已形成可复现的员工说明。
6. 正式文件与候选文件哈希一致。
7. Windows 更新服务回归验证通过。
8. 员工下载首页同时提供已验证的 Windows 与 macOS 安装包。
