# Codex 会话管理桌面端 UI 轻量科技化改版设计

## 背景

当前 macOS 桌面端已经具备完整的会话管理和快照恢复能力，但界面存在几个明显问题：

- 视觉风格偏重，面板和控件堆叠感强，不像成熟产品。
- 顶部和列表工具区容易拥挤，窄宽度下会出现按钮文字遮挡。
- 分栏拖拽能力弱，用户难以感知中间边界可拖动。
- “打开时自动找回”作为带副作用的行为，当前默认开启且视觉权重过高。

这轮改版不改变核心信息架构，不新增功能，以视觉重塑、布局重排、交互稳定性提升为主。

## 目标

将应用改造成“轻盈现代、年轻化、有科技感，但仍像成熟桌面产品”的体验。

具体目标：

- 减少厚重面板感，提升留白、层次和对齐质量。
- 明确主次操作，避免把危险操作和高频筛选动作挤在同一行。
- 提升分栏拖拽的可发现性和可操作性。
- 将自动恢复开关改为默认关闭，并降低其视觉优先级。
- 保持现有功能、文案语义和使用路径基本稳定，避免用户重新学习。

## 非目标

- 不引入新的功能页或复杂导航层级。
- 不重写数据模型或业务逻辑。
- 不把应用改成强装饰性的概念稿风格。
- 不做与本轮视觉改版无关的大规模组件化重构。

## 设计方向

本轮采用“轻盈专业”作为主风格，并向“年轻化、科技感”微调。

视觉语言：

- 以浅灰白为基底，减少大面积厚灰背景。
- 使用克制的电蓝色作为强调色，仅用于主按钮、选中态、关键图标和关键状态。
- 卡片采用轻描边、浅阴影、统一圆角，避免沉重的块状感。
- 字重层次明确：标题清晰、说明文字偏淡、数字和关键状态突出。
- 科技感通过秩序、密度控制、统一图标语言和精确对齐体现，而不是通过大面积渐变或强装饰。

## 页面级布局策略

应用保留当前三层结构：

- 左侧导航栏
- 中间列表与筛选区
- 右侧详情与操作区

但会重新分配每一层的视觉职责：

- 左侧负责“导航和当前状态概览”
- 中间负责“查找、筛选、选择”
- 右侧负责“理解详情、执行操作”

顶层工具栏只保留全局行为，不承载强设置感控件。

## 详细设计

### 1. 顶部栏

当前问题：

- 页面切换和“打开时自动找回”同时出现在高注意力区域，视觉主次不清。
- 蓝色开关过于醒目，像主功能而不是次级偏好设置。

改法：

- 页面切换继续使用 segmented control，但整体更紧凑，弱化“功能”字样的存在感。
- `刷新` 和 `打开目录` 继续保留在工具栏，作为全局操作。
- `打开时自动找回` 改为默认关闭。
- `打开时自动找回` 降级为次级设置项：
  - 仍可保留在顶部右侧，但视觉上使用更轻的容器和说明。
  - 不再占据整行视觉中心，不使用明显的高对比背景。

预期效果：

- 首屏更聚焦于页面内容。
- 用户不会把自动恢复误认为是当前页的主要操作。

### 2. 左侧导航栏

当前问题：

- 标题区略显松散，状态卡偏厚重。
- 选中态偏重，整体更像原型而不是产品。

改法：

- 压缩标题区高度，减少空耗。
- 说明文案保持存在，但降低颜色对比。
- `当前 Codex 状态` 卡片改为更轻的 info panel：
  - 更柔和的背景层
  - 更统一的内边距和圆角
  - 字段对齐更明确
- 导航选中态改为更克制、更贴近系统风格的高亮，不使用过重的满条蓝底。

预期效果：

- 左侧更像成熟桌面工具的导航面板。
- 状态信息清晰，但不会压过主内容。

### 3. 中间列表与工具区

当前问题：

- 搜索、筛选、全选、清空、删除选中等操作拥挤在一块。
- `删除选中` 在窄宽度下容易被截断。
- 批量操作缺乏层级，危险操作显得拥挤且突兀。

改法：

- 将工具区拆分为两层：
  - 第一层：搜索、筛选、输入类高频操作
  - 第二层：全选、清空选择、批量删除等批量操作
- `删除选中` 只在存在选择时出现，并保持独立的最小宽度，不参与压缩。
- 危险操作与普通筛选之间增加明确分组，不再连续堆叠。
- 在快照页中，创建快照保持为主按钮，但与筛选和批量删除分层摆放。
- 列表项选中态、标签、次信息层级统一成更现代的样式。

预期效果：

- 用户一眼就能区分“筛选”和“批量处理”。
- 窄窗口下也不会出现按钮文字被裁切的问题。

### 4. 右侧详情区

当前问题：

- 信息完整，但卡片层级偏平均，主次不够清晰。
- 主操作、辅助操作、高风险操作之间的视觉区分可以更明确。

改法：

- 顶部主信息区保留大标题和时间，但会更轻一些。
- 主操作卡只突出一个主按钮，例如 `只恢复对话`。
- 次级操作如 `打开快照目录` 作为辅助按钮保留。
- 指标卡保持信息密度，但统一卡面风格和留白。
- `高级恢复` 和 `删除快照` 继续保留在下方，通过弱化常态、强化风险提示来建立顺序。

预期效果：

- 用户先看到最安全、最推荐的操作。
- 页面更像成熟产品详情面板，而不是功能块堆叠。

### 5. 分栏拖拽体验

当前问题：

- 当前中间分割线虽然存在，但热区很窄，难以拖动。
- 用户不容易意识到分栏是可调整的。

改法：

- 提升分栏分隔区的交互热区宽度。
- 分隔视觉从“纯细线”改为“细线 + 更可感知的拖拽区域”。
- 在 hover 或接近拖拽时给予轻微反馈，让用户知道这里可操作。

预期效果：

- 分栏拖动更自然。
- 不需要精确点中一条线也能成功调整宽度。

## 交互与默认值调整

本轮需要明确落地以下行为：

- `打开时自动找回` 默认值改为关闭。
- 危险操作默认不抢占主视觉。
- 窄窗口下优先保持按钮可读，其次才压缩输入区。

## 实现建议

本轮实现应优先采用局部、可验证的 SwiftUI 调整，而不是大规模重写。

建议顺序：

1. 顶层导航和工具栏层级调整
2. 左侧栏样式轻量化
3. 会话页与快照页工具区重排
4. 详情卡片样式统一
5. 分栏拖拽热区增强
6. 默认开关值调整与回归验证

## 验证标准

完成后应满足以下标准：

- 快照页和会话页在常见窗口宽度下无按钮文字遮挡。
- `删除选中` 不会与筛选操作挤在同一压缩层级中。
- 中间分栏可被轻松拖动，用户无需精确点线。
- 自动找回开关默认关闭。
- 界面整体更轻、更年轻化，但仍保有成熟产品的稳定感。

## 风险与约束

- 视觉改动需尊重 SwiftUI 原生控件行为，避免为追求风格破坏可用性。
- 分栏拖拽增强需要优先考虑原生 split view 能力，避免引入脆弱的自定义拖拽实现。
- 不同窗口宽度下要关注控件换行与内容最小宽度，避免再次出现局部修一个、全局又挤压的问题。
