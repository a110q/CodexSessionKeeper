# Mac mini 局域网静态更新设计

**日期：** 2026-07-22

**适用分支：** `codex/nas-auto-update`

**状态：** 已确认设计，待实施计划

## 1. 目标

将 `codex_会话管理` 的公司内网更新源从绿联 NAS Docker 改为一台持续开机、具有固定内网 IP 的 Mac mini。Mac mini 使用原生 Nginx 提供只读静态文件；客户端固定使用该更新源，在发现新版后提示员工，由员工主动选择下载和重启安装。

本设计同时覆盖：

- 员工首次安装所需的内网下载页。
- Windows 客户端后续自动检查、下载校验和安装流程。
- 管理员发布新版本的顺序和失败保护。
- Mac mini 或内网服务不可用时的软件行为。

## 2. 非目标

- 不在绿联 NAS 上安装 Docker、Web 服务或更新文件。
- 不开放公网更新。
- 不建设数据库、账号系统或动态管理后台。
- 不实施强制更新、后台静默下载或自动降级。
- 不允许员工修改更新地址。
- 本设计不处理已发现的 Electron 多实例问题。

## 3. 已确认约束

- 更新服务仅供公司局域网访问。
- Mac mini 有固定内网 IP，并在工作时间持续开机联网。
- 服务使用独立 TCP 端口 `18080`。
- 客户端内置固定更新地址，员工界面不展示配置入口。
- 员工必须点击“立即更新”后才下载安装包。
- 具体固定 IP 是实施输入：正式构建前必须取得并从员工网段验证该地址；未验证前不得构建或分发正式安装包。

## 4. 总体架构

```text
员工首次安装
  Windows 浏览器
      -> Mac mini 固定内网 IP 的 18080 端口
      -> /codex-session-keeper/
      -> index.html
      -> 当前 Windows Setup.exe

后续更新
  codex_会话管理
      -> /codex-session-keeper/stable/release.json
      -> /codex-session-keeper/stable/release.json.sig
      -> 验签并比较版本/构建号
      -> 员工点击“立即更新”
      -> /codex-session-keeper/stable/windows/latest.yml
      -> /codex-session-keeper/stable/windows/<versioned Setup.exe>
      -> 大小和 SHA-256 校验
      -> 员工点击“重启并更新”
```

静态站点只是文件分发端，不主动向员工电脑发消息。客户端通过启动检查、周期检查或手动检查发现新版。

## 5. Mac mini 静态服务

### 5.1 服务方式

Mac mini 原生运行 Nginx，不依赖 Docker Desktop。Nginx 配置为开机自动运行，只提供静态文件，不启用脚本、反向代理、目录写入或动态接口。

服务必须满足：

- 监听固定内网 IP 的 `18080` 端口，或监听本机后由防火墙限制员工网段访问。
- 支持 `GET` 和 `HEAD`，并支持大文件下载与 Range 请求。
- 拒绝 `POST`、`PUT`、`DELETE` 等写请求。
- 禁止目录列表。
- 对 `release.json`、`release.json.sig` 和 `latest.yml` 禁用缓存或设置为每次重新验证。
- 对版本化 Setup.exe 允许长缓存，因为文件名包含版本且发布后不可变。
- Nginx 运行账号对站点目录只有读取权限。
- 发布账号可以写入发布目录，但员工和 Nginx 运行账号不能写入。
- Mac mini 防火墙只允许公司员工网段访问 `18080`，路由器不配置公网端口映射。

### 5.2 文件布局

```text
codex-update-site/
└── codex-session-keeper/
    ├── index.html
    └── stable/
        ├── release.json
        ├── release.json.sig
        └── windows/
            ├── latest.yml
            ├── CodexSessionKeeper-1.1.0-windows-x64-Setup.exe
            └── CodexSessionKeeper-1.2.0-windows-x64-Setup.exe
```

`index.html` 面向首次安装员工，显示产品名称、当前正式版本、发布日期、简短更新说明和“下载 Windows 安装包”按钮。自动更新客户端不解析该页面。

## 6. 客户端设计

### 6.1 固定地址

客户端使用一个编译时固定的发布根地址和其派生的 Windows feed 地址。不得从渲染进程、员工输入、命令行或远端清单接受替代地址。

迁移实施必须同步替换以下位置中的旧 NAS 地址：

- Windows `UpdateService` 默认发布根地址。
- Electron Builder 的 generic provider URL。
- 发布清单构建与验证脚本中的下载前缀。
- 自动化测试、部署文档和运维检查命令。

正式构建前，构建测试必须确认代码和生成产物中不再引用旧地址 `192.168.10.99:18080`。

### 6.2 检查策略

- 软件启动后约 5 秒检查一次；若持久化的上次检查时间尚未超过 8 小时，则延迟到满 8 小时再检查。
- 启动后维持每 8 小时一次的周期检查。
- 右上角保留“检查更新”按钮，员工可随时手动检查。
- 下载中、校验中或已有待安装更新时，不并发发起新的检查。
- 自动检查连接失败时保持静默，不影响软件主功能。
- 手动检查连接失败时显示“暂时无法连接公司更新服务器，请稍后重试”。

### 6.3 更新状态流

```text
idle
  -> checking（仅手动检查显示）
  -> up-to-date | available | failed

available
  -> 员工选择“稍后提醒”：关闭弹窗，不下载
  -> 员工选择“立即更新”：downloading

downloading
  -> verifying
  -> ready | failed

ready
  -> 员工选择“稍后重启”：保留已验证安装包
  -> 员工选择“重启并更新”：排空备份并安装

安装后的首次启动
  -> completed
  -> 员工选择“知道了”：idle
```

客户端保持：

- `autoDownload = false`
- `autoInstallOnAppQuit = false`
- `allowDowngrade = false`

### 6.4 信任与校验

客户端首先下载 `release.json` 和 `release.json.sig`，使用内置 Ed25519 公钥验证清单原始字节，然后选择 `windows-x64` 产物并比较语义版本与整数构建号。

员工点击“立即更新”后，客户端读取 `windows/latest.yml`，并在下载前要求：

- feed 版本与已验签清单版本一致。
- 所有下载 URL 都位于固定 Windows feed 目录下。
- URL、文件名和已验签清单中的目标完全一致。

安装包下载完成后继续要求：

- 下载事件版本一致。
- 路径为绝对路径。
- 目标是普通文件且不是符号链接。
- 文件字节数与清单一致。
- SHA-256 与清单一致。

任一条件失败时只删除本次下载的临时安装包，进入失败状态，不运行安装器。

HTTP 只用于局域网传输；更新真实性和完整性由签名、固定 URL 边界、大小及 SHA-256 共同保证。后续如公司提供受信任的内网域名和证书，可迁移到 HTTPS，但不改变更新状态机。

### 6.5 安装与备份协调

点击“重启并更新”后：

1. 本地增量备份最多等待 5 秒停止并排空写入。
2. 排空失败则恢复备份轮询，取消重启并提示稍后重试。
3. 排空成功后写入待完成版本标记。
4. 调用 Electron Updater 退出并运行已验证安装包。
5. 新版本首次启动消费完成标记并显示“已更新到 X.Y.Z”。

更新不得删除或覆盖会话、快照、设置、增量游标和备份配置。

## 7. 发布设计

### 7.1 候选版本

管理员先在非正式目录组装候选版本，并运行现有发布目录验证工具。候选版本必须通过：

- 清单签名验证。
- 版本、构建号和平台验证。
- `latest.yml` 与 Setup.exe 名称/版本一致性验证。
- 安装包实际大小和 SHA-256 验证。
- 路径和 URL 均在允许目录内。

### 7.2 发布顺序

正式目录的更新顺序固定为：

1. 版本化 Setup.exe。
2. `windows/latest.yml`。
3. `release.json.sig`。
4. `release.json` 最后发布。

客户端只把最后出现的有效 `release.json` 视为新版本正式可见的信号。发布操作应在同一文件系统内通过临时文件和原子重命名完成，避免员工读取到半写文件。

版本化安装包一旦发布不得用不同内容覆盖。默认保留当前正式版本及前两个稳定版本；旧版只供排查，不向客户端提供自动降级。

### 7.3 下载页更新

自动更新目录发布成功后再更新 `index.html`，使首次安装页指向新的正式安装包。下载页失败不会影响已安装客户端通过 `release.json` 更新。

## 8. 失败行为

| 场景 | 客户端行为 |
|---|---|
| Mac mini 关机、休眠或断网 | 主功能继续运行；自动检查静默失败，手动检查显示连接提示 |
| 清单尚未最后发布 | 客户端继续看到旧版本 |
| 清单或签名被修改 | 拒绝更新并显示安全失败信息 |
| `latest.yml` 与清单不一致 | 下载前拒绝 |
| Setup.exe 上传不完整或被修改 | 下载后校验失败并删除临时安装包 |
| 下载中断 | 进入失败状态，允许员工稍后重试，不影响会话与备份 |
| 备份正在写入且无法排空 | 取消安装重启并恢复备份轮询 |
| 新版本存在应用缺陷 | 修复后发布更高版本，例如 `1.2.1`；不降低清单版本 |

## 9. 验证计划

### 9.1 静态服务

- 员工网段可以访问下载页、清单、签名、`latest.yml` 和 Setup.exe。
- 非允许网段无法访问 `18080`。
- `GET`、`HEAD` 和 Range 下载成功。
- 写请求被拒绝，目录列表不可见。
- Mac mini 重启后 Nginx 自动恢复服务。

### 9.2 首次安装

- 在干净的 Windows 标准用户账户打开内网下载页。
- 下载并安装测试基线 `1.0.99`，不要求管理员提升。
- 软件正常启动，会话、快照和本地增量备份可用。

### 9.3 自动更新验收

在静态服务发布 `1.1.0`，验证：

- 启动自动检查和右上角手动检查均能发现新版。
- “稍后提醒”不下载安装包。
- “立即更新”显示递增的字节和百分比进度。
- 下载后验证大小和 SHA-256。
- “稍后重启”不安装且继续正常工作。
- “重启并更新”先排空备份，再覆盖安装并重新启动。
- 新版本显示更新完成提示。
- 会话、快照、设置、增量游标和备份配置保持不变。

### 9.4 负向测试

- 断开 Mac mini 网络。
- 发布无效签名。
- 让 `latest.yml` 指向错误文件。
- 修改 Setup.exe 一个字节。
- 下载过程中断开网络。
- 模拟备份无法在 5 秒内排空。

所有负向测试都必须证明：错误安装包不会执行，主功能和用户数据不受影响。

## 10. 实施边界与完成标准

实施分为三个独立阶段：

1. 修改并测试客户端和发布工具中的固定地址。
2. 在 Mac mini 上安装、配置并验证原生 Nginx 静态服务。
3. 在 Windows 测试电脑完成 `1.0.99 -> 1.1.0` 端到端更新验收。

完成标准为：端到端验收和全部负向测试通过；正式构建不引用旧 NAS 地址；NAS 未发生任何变更；Mac mini 服务重启可恢复；员工只能主动下载和主动重启安装。
